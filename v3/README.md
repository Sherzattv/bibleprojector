# Bible Projector v3

Основная и единственная активная линия разработки Bible Projector на
Svelte 5, TypeScript, Vite и Tailwind CSS 4.

Текущая версия: **3.3.1** — этот номер стоит в `package.json` и показывается
в шапке пульта. Часть релизных требований ещё открыта, они перечислены
в [`ROADMAP.md`](../ROADMAP.md). Runtime v2 удалён; исходные базы находятся
в `data/source/`.

## Возможности

Что умеет приложение для оператора, перечислено в
[корневом README](../README.md#что-работает-в-v3) — список ведётся в одном
месте. Этот документ — техническая сторона: запуск, архитектура, данные,
сборка и деплой.

## Текущие ограничения

- нет предупреждения оператору, когда autofit ужимает текст до минимума;
- дополнительные темы проекционного экрана не реализованы;
- браузерные E2E покрывают шесть критических сценариев; раскладка на всех
  поддерживаемых разрешениях и полностью офлайн-запуск ими не проверяются;
- планшеты и телефоны не являются поддерживаемыми платформами;
- `npm audit` сообщает о dev-цепочке `vite-plugin-pwa`; production-зависимости
  проходят `npm audit --omit=dev` без уязвимостей.

Актуальные приоритеты и критерии релиза находятся только в
[`ROADMAP.md`](../ROADMAP.md).

## Требования

- Node.js 22;
- npm;
- исходные данные в `data/source/` для полной локальной сборки;
- desktop-версия Chromium;
- окно пульта не меньше `1280×720`.

Экран проектора открывается через Presentation API: браузер сам показывает
выбор монитора и открывает экран там во весь экран. Выбор монитора из меню
пульта, офлайн-режим и браузеры без этого API получают обычное popup-окно,
которое Window Management API ставит на нужный монитор, если браузер его
поддерживает и оператор дал разрешение. Подробности — в разделе
[«Второй монитор»](../README.md#второй-монитор) корневого README.

Пульт оператора проектируется и тестируется только для desktop. Существующая
узкая раскладка с выдвижными панелями — аварийный fallback без гарантии
полной работоспособности на планшетах и телефонах. Экран проектора
рассматривается отдельно и должен корректно работать в форматах 16:9 и 4:3.

## Локальный запуск

Из каталога `v3/`:

```bash
npm ci
npm run data
npm run dev
```

Vite покажет локальный адрес. Пульт доступен по `/`, экран проектора — по
`/#display`. Обычно экран удобнее открывать кнопкой «Открыть экран», чтобы
сработало размещение на внешнем мониторе.

`npm run data` выполняет:

1. чтение RST, NRT, KTB, KYB и песен из `data/source/`;
2. удаление дублирующихся VerseId и пустых стихов;
3. проверку структуры всех 66 книг;
4. запись полных JSON в `public/data/`;
5. создание контент-хэшированного `manifest.json`;
6. создание небольшого demo-набора.

`public/data/` и `src/lib/demo-data.json` генерируются локально и
игнорируются Git.

Полная локальная проверка:

```bash
npm run check
npm test
npx playwright install chromium
npm run test:e2e
npm audit --omit=dev
```

Установка Chromium нужна один раз на рабочую машину. E2E запускаются
только локально перед релизами; CI держит быстрый набор — типы, модульные
тесты, демо-сборку одним файлом, production-сборку и дымовой тест раздачи.

## Архитектура

```text
v3/
├── scripts/
│   ├── convert-data.mjs       # Полная конвертация
│   └── convert-core.mjs       # Очистка, валидация и хэши
├── public/data/               # Генерируемые JSON и manifest
├── e2e/                       # Браузерные сценарии Playwright
├── playwright.config.ts       # Production-preview и Chromium
├── src/
│   ├── main.ts                # Пульт или экран проектора (#display)
│   ├── App.svelte             # Раскладка пульта оператора
│   └── lib/
│       ├── bible/             # Книги, BookId переводов, ссылки на стихи
│       ├── songs/             # Разбиение песен на слайды
│       ├── data/              # Загрузка переводов и песен, кэш, запуск
│       ├── search/            # MiniSearch, Web Worker, клиент, выдача Omnibox
│       ├── show/              # Превью и эфир, команды, история, порядок, правки
│       ├── projection/        # Что рисует экран: протокол, настройки,
│       │                      #   переходы, autofit, служебные экраны
│       ├── projector/         # Окно проектора: связь, Presentation API,
│       │                      #   мониторы, медиа и поведение окна экрана
│       ├── media/             # Свои файлы оператора: протокол и IndexedDB
│       ├── backgrounds/       # Живые фоны: каталог, шейдеры, рендер
│       ├── ui/                # Уведомления, раскладка панелей, хоткеи
│       ├── utils/             # localStorage, форматирование, текст, файлы
│       └── components/
│           ├── header/        # Шапка: поиск, экран, фон, настройки
│           ├── workspace/     # Библиотека, превью/эфир, слайды, док, порядок
│           ├── display/       # Экран проектора
│           ├── projection/    # Общее для экрана и карточек пульта
│           └── ui/            # Примитивы: Popover, RangeField, сегменты
└── tests/                     # Повторяют структуру src/lib
```

Модули с реактивным состоянием (руны `$state`, `$effect`) называются
`*.svelte.ts`; остальные его не держат. Чистая логика — разбор, нормализация,
расчёты — живёт в отдельных модулях без рун и DOM и покрыта модульными
тестами. Компоненты не меняют состояние эфира напрямую: все действия
оператора идут через `show/commands.svelte.ts`.

### Где что менять

| Задача | Куда |
| --- | --- |
| Новое действие оператора (кнопка, хоткей) | команда в `show/commands.svelte.ts`, хоткей — в `ui/hotkeys.ts` |
| Новая настройка экрана | поле и нормализация в `projection/content.ts`, сеттер в `projection/settings.svelte.ts`, контрол в `components/header/ProjectionSettingsPanel.svelte` |
| Новое сообщение пульт ↔ экран | `projector/link.svelte.ts`; экран принимает его в `components/display/DisplayView.svelte` |
| Что показывает экран | `projection/content.ts` (`buildContent`) и `components/display/` |
| Новая выпадающая панель, ползунок, переключатель | примитивы из `components/ui/` и классы из `components/ui/styles.ts`, правила — в [`DESIGN.md`](src/lib/DESIGN.md) |
| Новая книга, сокращение или перевод | `bible/books.ts`, перевод — ещё `TRANSLATIONS` в `data/db.svelte.ts` и `scripts/convert-data.mjs` |
| Сохранение в localStorage | `readJson`/`writeJson` из `utils/storage.ts`; всё прочитанное проходит нормализацию |

Тест кладётся в `tests/` по тому же пути, что и модуль: `src/lib/bible/books.ts`
→ `tests/bible/books.test.ts`.

### Данные и офлайн

RST и песни блокируют только начальную готовность приложения. NRT, KTB и
KYB загружаются в фоне; ошибка одного перевода не роняет пульт.

Оболочка приложения кэшируется Service Worker. JSON-файлы загружаются по
манифесту контент-хэшей и сохраняются в Cache Storage. При обновлении
перекачиваются только изменившиеся данные; при сетевой ошибке допустим
stale-fallback из локального кэша.

Кэш данных (`data/cache.ts`) держит несколько инвариантов — каждый из них
закрывает отказ, который уже случался в проде:

- **Ответ разбирается до записи.** Иначе `200 + HTML` от неверно
  настроенного хостинга ложится в Cache Storage под видом данных.
  Дополнительно ответ проверяется по `content-type`.
- **Хэш считается от полученного тела**, а не берётся из манифеста. Иначе
  устаревшая копия файла запоминается под новым хэшем и больше никогда не
  перекачивается.
- **Битый кэш самолечится**: чтение кэша обёрнуто в `try`, при сбое запись
  удаляется и данные перечитываются из сети. Без этого один плохой ответ
  делал перевод неработоспособным навсегда — перезагрузка не помогала,
  потому что до сети дело уже не доходило.
- **Кэш — оптимизация, а не условие запуска.** Сбой Cache Storage
  (переполнение квоты, приватный режим Firefox) не выбрасывает уже
  загруженные данные.
- Загрузка идёт с таймаутом, а провал стартовой загрузки даёт кнопку
  «Повторить» (`retryInit()`), а не тупик.

### Обновление версии

Новый Service Worker **не перехватывает работающие окна**: он ждёт в
`waiting` и активируется, когда оператор закроет все окна после служения.
Пульт и окно проектора связаны `BroadcastChannel` и обязаны работать на
одной версии оболочки — подмена посреди эфира рассинхронизировала бы их
формат сообщений. Вкладка пульта раз в час сама проверяет наличие новой
версии, чтобы обновление не опаздывало ещё на одно служение.

Кнопка «Обновить» в шапке (`components/header/UpdateButton.svelte`)
появляется, когда `main.ts` шлёт в `window` событие `bp3:update-ready`.
Второе нажатие отправляет экрану проектора команду перезагрузиться и шлёт
`bp3:apply-update` — по нему новый SW берёт управление и пульт
перезагружается, а экран перезагрузится, как только SW сменится и у него.

### Поиск

UI отправляет запросы через `SearchClient`. Клиент делает debounce, Worker
строит отдельный индекс для каждого загруженного перевода и отбрасывает
устаревшие ответы по sequence number. Точная ссылка обрабатывается до
fuzzy-поиска.

Книги Библии адресуются каноническим кодом OSIS (`JHN`, `1CO`) из
`lib/bible/books.ts`: по нему сопоставляются переводы, хранятся правки,
порядок служения и история. BookId — только адрес книги внутри файла
перевода, и он у переводов разный: в KTB соборные послания стоят перед
посланиями Павла. `lib/bible/reference.ts` разбирает ввод оператора
(«ин 3 16», «жар 1:1») в ссылку.

### Эфир и внешний экран

Все пользовательские действия проходят через `show/commands.svelte.ts`.
`show/show.svelte.ts` хранит Preview/Live, `projector/sync.svelte.ts`
собирает из него проекционный DTO, а `ProjectorLink` отправляет DTO и
настройки экрану: попапу — по BroadcastChannel, экрану Presentation API —
через PresentationConnection (он живёт в изолированном профиле, куда
BroadcastChannel не доходит). Экран отвечает heartbeat, поэтому статус
подключения в пульте отражает реальное окно, а вместе с heartbeat приходят
признак fullscreen и замер контраста фона.

### Живой фон

`lib/backgrounds/` — каталог фонов и палитр, GLSL-сцены и `BackgroundRenderer`.
Фон рисуется на экране проектора и в карточках «Превью»/«Эфир» пульта: один WebGL-canvas на все шейдеры
(программы компилируются лениво) и Canvas 2D для потока частиц. Чтобы не
нагружать слабый ноутбук, фон рендерится в доле разрешения (по умолчанию 50%)
с потолком 30 к/с, а чёрный фон цикл не запускает вовсе. Раз в секунду экран
меряет контраст белого текста с фоном (95-й перцентиль яркости в центре кадра)
и отправляет его в пульт вместе с heartbeat. Карточки пульта рисуют тот же
фон в облегчённом режиме (50% разрешения, не больше 30 к/с): прежняя CSS-копия
из пятен палитры не давала понять, как выглядят горы или свечи.

Свои файлы оператора (фон и логотип) лежат в IndexedDB пульта
(`media/library.svelte.ts`). В настройки проекции уходят только их версии;
сам файл экран запрашивает сообщением `media-request` и получает `media` с
data-URL. Так один путь работает и для попапа, и для экрана Presentation API
в изолированном профиле, где чужая IndexedDB не видна.

Порядок, история, настройки и правки текста сохраняются локально. Серверная
синхронизация и аккаунты отсутствуют.

## Production-сборка и деплой

Из корня репозитория:

```bash
npm run build
```

Команда устанавливает зависимости v3 по lock-файлу, заново генерирует
данные и собирает публикуемый каталог `dist/` в корне репозитория:
лендинг из `site/` плюс приложение (сборка с base `/app/`) в `dist/app/`.

```bash
npm run deploy
```

Команда запускает production-сборку и публикует `dist/` через Cloudflare
Workers Static Assets. Лендинг работает на корневом URL, приложение — на
`/app/`; временный путь `/next/` больше не используется.

В Cloudflare Workers Builds нужно задать `npm run build` как Build command
и оставить `npx wrangler deploy` как Deploy command. Эти строки живут в
дашборде: Workers Builds не читает секцию `build` из `wrangler.jsonc`.

Перед деплоем прогоняйте дымовой тест раздачи из корня репозитория:

```bash
npm run smoke
```

Он поднимает `wrangler dev` на собранном `dist/` и проверяет реальными
запросами, что `/app/` отдаёт приложение, а не лендинг, и что
несуществующие пути получают 404. Параметры раздачи (`html_handling`,
`not_found_handling`) описаны в [корневом README](../README.md#раздача-статики) —
оба уже ломали прод, и `wrangler deploy --dry-run` их не проверяет.

## Правила дальнейшей работы

- новый продуктовый код создаётся только в `v3/`;
- runtime и UI v2 удалены и не возвращаются в проект;
- исходные базы хранятся только в `v3/data/source/`;
- каждое изменение поведения сопровождается тестом и записью в changelog;
- новые задачи добавляются в `ROADMAP.md`, а не в архивные документы.
