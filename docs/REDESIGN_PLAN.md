# Bible Projector 3.0 — исходный план редизайна (архив)

> **Статус документа:** историческое проектное предложение, на основании
> которого была начата v3. Это не описание текущей архитектуры и не backlog.
> Актуальные источники: [`v3/README.md`](../v3/README.md) и
> [`ROADMAP.md`](../ROADMAP.md).

Реализация осознанно разошлась с некоторыми ранними решениями этого плана:
данные хранятся как JSON в Cache Storage, а не через Dexie/IndexedDB;
production-сборка использует PWA Service Worker и контент-хэшированный
манифест вместо Brotli-чанков; критические сценарии покрыты Playwright E2E.
Не реализованы Document Picture-in-Picture, Presentation API, stage display
и сетевой режим. Ниже сохранён исходный текст для истории решений.

Цель: сохранить существующие данные (4 перевода Библии + каталог песен),
но полностью обновить UX/UI, поднять поиск и работу со вторым экраном на
уровень профессиональных систем (ProPresenter / FreeShow / OpenLP), не
изобретая велосипедов — только зрелые, стандартные технологии.

---

## 1. Диагностика текущего состояния

**Что хорошо и остаётся:**
- Данные: RST, NRT, KTB, KYB + 11 524 песни (OpenLP-экспорт) — сохраняем как есть по содержанию.
- Канонические коды книг (`canonical.js`) — правильная основа для кросс-переводного поиска.
- PWA + offline (Service Worker), деплой на Cloudflare Workers Static Assets.
- BroadcastChannel + Multi-Screen Window Placement API — верное направление.
- Есть тесты (vitest) и линт.

**Главные проблемы:**
1. **~43 МБ данных грузятся синхронно** пятью `<script src>` в `controller.html`
   как глобальные переменные (`window.BIBLE_DATA` и т.д.). Это блокирует старт,
   съедает память (все 4 перевода всегда в RAM) и делает первый запуск тяжёлым.
2. **Поиск наивный**: `includes()` по всем стихам в главном потоке — нет
   ранжирования, опечаток, префиксов, ё/е-нормализации в Библии, подсветки;
   три разных модалки (ссылка / текст / песни) вместо одного умного поля.
3. **UI написан императивно** (onclick-глобалы, ручной DOM), без сборки и
   типов — масштабировать дизайн на этом фундаменте дорого.
4. **Нет ключевых сценариев служения**: плейлист (порядок служения),
   раздельные Preview/Live, сетка слайдов песни, blackout/логотип, темы экрана.

## 2. Технологический стек (без велосипедов)

| Слой | Выбор | Почему |
|---|---|---|
| Сборка | **Vite + TypeScript** | Стандарт де-факто, нулевая конфигурация, HMR, code-splitting |
| UI-фреймворк | **Svelte 5** (альтернатива: Preact) | Минимальный рантайм-вес (важно для PWA), простая реактивность, идеален для соло-разработки |
| Стили | **Tailwind CSS 4 + CSS-переменные тем** | Дизайн-система без самописного CSS-фреймворка; текущий `variables.css` эволюционирует в токены |
| Хранение данных | **IndexedDB (Dexie.js)** с чанкованной загрузкой | Переводы и песни один раз скачиваются, дальше живут локально; в память грузится только нужный перевод |
| Поисковый движок | **MiniSearch** (или Orama) в **Web Worker** | Готовый инвертированный индекс: fuzzy (опечатки), префиксы, BM25-ранжирование, boosting полей. Работает офлайн, ~7 КБ gzip |
| Состояние | Svelte stores / runes | Ничего внешнего не нужно |
| Тесты | Vitest (уже есть) + Playwright для e2e | Playwright уже в devDependencies |
| Деплой | Cloudflare Workers (как сейчас) | Ничего не менять |

Данные конвертируются один раз скриптом (у нас уже есть `scripts/convert_*.py`
и исходные SQLite-модули в `bible module/` и `archive/sources/`):
`data/rst.json.br`, `nrt.json.br`, … `songs_ru.json.br` — статические
брótли-сжатые чанки (~1–2 МБ каждый вместо 7–14 МБ JS). Первый запуск:
скачали → положили в IndexedDB → построили индекс в воркере → закэшировали.

## 3. «Самый умный поиск» — единый Omnibox

Одно поле ввода в стиле command palette (Cmd+K), которое само понимает, что
ввёл пользователь, и показывает смешанные результаты мгновенно (по мере ввода,
debounce ~120 мс, поиск в Web Worker — UI никогда не тормозит):

1. **Ссылка на стих** — существующий парсер (`ин 3 16`, `1 кор 13:4-8`,
   `жар 1:1`) остаётся, расширяется: диапазоны глав, «ин 3» → вся глава,
   автодополнение книг при вводе («ио…» → Иоанна, Иов, Иона).
2. **Полнотекстовый поиск по Библии** (MiniSearch-индекс на перевод):
   - опечатки (fuzzy 0.2) и префиксы: «возлюб» находит «возлюбил»;
   - нормализация ё/е, регистра, пунктуации (уже есть для песен — обобщаем);
   - BM25-ранжирование + подсветка совпадений в результатах;
   - фильтр ВЗ/НЗ/книга, поиск сразу по нескольким переводам.
3. **Песни**: по номеру («579»), названию, теме, любой строке текста —
   с boosting'ом (название > номер > припев > текст), fuzzy для опечаток.
4. **Смешанная выдача с группами**: «Стихи · Песни · История» — как в
   Spotlight. Стрелки + Enter = показать, Ctrl+Enter = сразу в эфир.

Итог: три текущие модалки исчезают, остаётся одно поле (это же пункт №1
текущего ROADMAP «Единый поиск»).

## 4. Новый UX: рабочее место оператора

Раскладка как у профессиональных систем — три зоны:

```
┌──────────┬──────────────────────────┬───────────────┐
│ Плейлист │  PREVIEW      LIVE       │  Библиотека / │
│ (порядок │  (следующий)  (в эфире)  │  Omnibox /    │
│ служения)│  [сетка слайдов песни]   │  История      │
└──────────┴──────────────────────────┴───────────────┘
│  Транспорт: ⬅ ➡ слайды · GO · Blackout · Логотип · Очистить  │
```

- **Плейлист (порядок служения)** — главный новый сценарий: заранее собрать
  список (песни, стихи, заметки), во время служения только листать.
  Сохраняется локально, экспорт/импорт JSON.
- **Preview / Live** — стандарт индустрии: оператор видит и готовит следующий
  слайд, не трогая эфир. Кнопка GO переводит Preview → Live.
- **Сетка слайдов песни** — все куплеты/припевы плитками, клик = в эфир
  (сплит на секции уже реализован в `songs.js` — переиспользуем).
- **Транспорт-панель**: Blackout (чёрный экран без закрытия окна), показать
  логотип/фон, очистить текст — то, что в ROADMAP «Управление экраном».
- **Клавиатура прежде всего**: пробел/стрелки — слайды, B — blackout,
  L — логотип, Esc — очистить, Cmd+K — поиск. Всё как сейчас, но полнее.
- **Мобильный режим**: контроллер адаптивен (уже частично есть) — телефон
  как пульт.
- Редактирование стиха/песни на лету и заметки — сохраняются (перенос
  текущих localStorage-правок при миграции).

Дизайн: спокойная тёмная тема по умолчанию (операторская), светлая опционально,
токены в CSS-переменных, никакого «стеклянного» шума — контент и скорость.

## 5. Второй экран: современные API (2025–2026)

Базово остаётся окно `display.html` + BroadcastChannel, но добавляем:

1. **Window Management API** (доразвить текущее `getScreenDetails`):
   - permission `window-management`, запоминание выбранного монитора
     (`screen.label`), автоматическое открытие именно на проекторе;
   - **`requestFullscreen({ screen })`** — сразу в полный экран на нужном
     мониторе, без ручного F11;
   - событие `screenschange` — проектор подключили/отключили → авто-переоткрытие.
2. **Screen Wake Lock API** — экран проектора никогда не гаснет во время
   служения (сейчас может уснуть).
3. **Document Picture-in-Picture** — маленькое всегда-поверх-окон превью
   «что сейчас в эфире» для оператора.
4. **Presentation API** — прогрессивное улучшение для Chromecast/Miracast:
   трансляция display-страницы на беспроводной экран, где это поддержано.
5. **Темы и переходы экрана**: несколько готовых тем (текст/фон/градиент,
   позиция, тень), плавные fade/slide-переходы между стихами, автоподбор
   размера шрифта под объём текста (сейчас — фикс-слайдер).
6. **(Фаза 2, опционально) Сетевой режим**: Cloudflare Durable Objects +
   WebSocket — «комната» с кодом, чтобы пульт был на телефоне, а экран на
   другом компьютере (сцена/фойе/трансляция в OBS через browser source).
   Инфраструктура Cloudflare уже используется — это естественное расширение.
7. **Stage display (фаза 2)** — отдельный вид для служителей на сцене:
   текущая + следующая строка, часы.

## 6. Поэтапный план работ

**Фаза 0 — фундамент (1 неделя)**
- Vite + TypeScript + Svelte, перенос модулей (`canonical`, `songs`,
  `history`, `settings` почти без изменений), миграция vitest-тестов, CI-линт.

**Фаза 1 — данные (1 неделя)**
- Скрипт конвертации → сжатые JSON-чанки; загрузчик в IndexedDB (Dexie);
  ленивая загрузка переводов; прогресс первого запуска; обновление SW-кэша.

**Фаза 2 — поиск (1–2 недели)**
- MiniSearch-индексы (Библия по переводам + песни) в Web Worker;
  Omnibox с распознаванием типа запроса, ранжированием, подсветкой,
  клавиатурной навигацией. Тесты на парсер и релевантность.

**Фаза 3 — UI оператора (2–3 недели)**
- Дизайн-токены и компонентная база; раскладка Плейлист/Preview+Live/Библиотека;
  сетка слайдов; транспорт-панель (GO, Blackout, логотип, очистка);
  горячие клавиши; адаптив для планшета/телефона.

**Фаза 4 — экран трансляции (1–2 недели)**
- Window Management (fullscreen на выбранном мониторе, автопереоткрытие),
  Wake Lock, PiP-превью, темы + переходы + авторазмер шрифта.

**Фаза 5 — PWA и миграция (3–5 дней)**
- Оффлайн-стратегия для чанков данных, миграция localStorage (история,
  правки, настройки) в новую схему, обновление сайта/скриншотов/README.

**Фаза 6 — опционально, «новый уровень+»**
- Сетевой пульт (Durable Objects), Stage display, Presentation API,
  импорт своих песенников (OpenLP/txt), параллельный показ двух переводов
  (Split Screen из ROADMAP).

Принцип миграции: новая версия разрабатывается в `app/` на новом стеке рядом
со старой (старая доступна как `app/legacy/` до конца фазы 5), URL и PWA-scope
не меняются — пользователи получают обновление бесшовно.

---

## 7. Что явно НЕ делаем (анти-велосипед)

- Не пишем свой поисковый движок — берём MiniSearch/Orama.
- Не пишем свой стейт-менеджер, роутер, CSS-фреймворк.
- Не тащим тяжёлые фреймворки/Electron — остаёмся PWA (это преимущество).
- Не меняем формат исходных данных (SQLite-модули) — только конвейер доставки.
- Не строим бэкенд без нужды — всё offline-first; сервер появляется только
  в фазе 6 и только для сетевого пульта.
